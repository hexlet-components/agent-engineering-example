# Сервис фонового триажа

На этом стенде агент на OpenAI Agents SDK разбирает тикет, сотрудник проверяет предложенный вопрос, а автор сообщает недостающий факт. Temporal сохраняет ход работы. В учебном режиме модель выдаёт подготовленные ответы и вызывает инструмент чтения через SDK. Внешний ключ для этого режима не нужен.

## Запуск

Понадобятся Node.js 26, npm и Temporal CLI в PATH. Установите CLI по [руководству Temporal](https://docs.temporal.io/cli/setup-cli). Из каталога `production` установите зависимости и запустите Temporal. На диске появится база истории `temporal.sqlite`.

```bash
npm ci
npm run temporal
```

Во втором терминале из того же каталога запустите учебный трекер. Переменная `LOSE_REPLY` включает обрыв соединения после первой записи каждого нового комментария. Трекер сохраняет тикеты и комментарии в `var/tracker.sqlite`.

```bash
LOSE_REPLY=1 npm run server
```

В третьем терминале доставьте одно событие дважды. Откройте [Temporal UI](http://localhost:8233) и найдите `triage-T-42-v1`. Пока воркер выключен, история заканчивается постановкой первого задания в очередь.

```bash
npm run demo -- deliver T-42
npm run demo -- deliver T-42
```

В четвёртом терминале запустите воркер с имитацией сбоя. После получения первого ответа модели он завершится с кодом 23. Запустите обычный воркер. Через 15 секунд истечёт тайм-аут незавершённой Activity и Temporal разрешит новую попытку.

```bash
CRASH_AFTER_MODEL=1 npm run worker
npm run worker
```

Проверьте состояние в третьем терминале. Когда появится шаг `approval`, прочитайте вопрос. Команда `status` сохраняет показанный вопрос для одобрения. Можно остановить и снова запустить воркер в этот момент. При продолжении он получит уже записанный результат Activity из истории.

```bash
npm run demo -- status T-42
npm run demo -- approve T-42
```

Дождитесь шага `reply`. При потере ответа трекера воркер ищет запись по устойчивому ключу действия. Сопоставьте полученный `commentId` с идентификатором из трекера. Отправьте ответ автора.

```bash
npm run demo -- status T-42
curl http://127.0.0.1:3030/comments/triage-T-42-v1%2Fquestion
npm run demo -- reply T-42 'Без фильтра строки есть'
npm run demo -- status T-42
```

В состоянии `completed` появится рекомендация проверить связь с дефектом T-17. Доставьте то же событие ещё раз и сравните Run ID в интерфейсе. В пределах срока хранения истории Temporal отклоняет повторный запуск с прежним Workflow ID.

## Другие опыты

Чтобы заново пройти шаги на том же стенде, создайте следующую редакцию тикета. Команда `revise` выводит её номер. Подставьте его в переменную для дальнейших команд с этим тикетом. В другом терминале переменную нужно задать заново. Для первого запуска другого тикета укажите версию 1.

```bash
npm run demo -- revise T-42 'При экспорте CSV получаю пустой файл.'
export TICKET_VERSION=2
npm run demo -- deliver T-42
```

- Для проверки отказа просмотрите вопрос через `status` и отправьте `reject` вместо `approve`. Для проверки устаревшего решения измените версию тикета после просмотра и отправьте одобрение прежней версии. Трекер сверяет версию перед записью.
- Для проверки лимита доработок запустите воркер с `BAD_DRAFT=1` и доставьте свежий тикет. После двух пустых ответов его разбор переходит сотруднику.
- Для сравнения задержек остановите воркер, доставьте T-44 и T-45 с интервалом в несколько секунд и снова запустите воркер. Найдите время ожидания первого задания в каждой истории. Число одновременно выполняющихся Activity задаёт `ACTIVITY_SLOTS`.
- Для сравнения версий выполните `npm run eval`. На трёх тикетах вариант v1 ошибочно связывает T-44 с известным дефектом, вариант v2 проходит все три проверки. Promptfoo возвращает код 100 при проваленном критерии. Это воспроизводимая демонстрация сравнения на подготовленных ответах. Для отдельного опыта с внешней моделью задайте `OPENAI_MODEL` и `OPENAI_API_KEY` в окружении воркера или процесса Promptfoo.
- Перед запуском сервера задайте `POLICY_VERSION=v2` и `ROLLOUT_PERCENT=10`, чтобы разрешить публикацию для выбранных по хешу 10 процентов ключей тикетов. В режиме `ROLLOUT_PERCENT=0` сервис завершает разбор с черновиком. Workflow получает политику и разрешение при старте и использует их после перезапуска.

Сервер слушает только локальный интерфейс. В стенде команды сотрудника и автора воспроизводят события доверенного адаптера трекера. Ключ `TRACKER_KEY` нужен Activity публикации и серверу. Для локального примера у них одинаковое учебное значение. Инструмент агента читает только входную версию тикета и карточку известного дефекта.
